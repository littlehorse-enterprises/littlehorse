# The serde rules

The recipe for the serde area. It defines how every SDK converts a native
language value into a `VariableValue` proto (the encoding the whole
platform stores and ships). As with the builder rules, **the fixtures are
the authority**, and this prose restates them so an implementer never
reverse-engineers another SDK. A divergence here never errors at runtime.
It silently changes data crossing a language boundary, which is why the
area exists.

## Typed inputs (S1)

Languages disagree about values (JS has no int/double distinction, and
JSON numbers are lossy above 2⁵³), so a case's input is typed, and each
testee maps it to its native value before calling its converter:

| `input.type` | `input.value` in the manifest | Java native | JS native |
| --- | --- | --- | --- |
| `str` | the string | `String` | `string` |
| `int` | decimal string, never a JSON number (S4) | `Long` | `bigint` |
| `double` | decimal string | `Double` | `number` |
| `bool` | `"true"` / `"false"` | `Boolean` | `boolean` |
| `bytes` | base64 string | `byte[]` | `Buffer` |
| `timestamp` | epoch-millis decimal string | `Instant` | `Date` |
| `json-obj` | JSON object as text (S5) | `Map` (parsed) | parsed object |
| `json-arr` | JSON array as text (S5) | `List` (parsed) | parsed array |
| `null` | *(absent)* | `null` | `null` |

The runner hands the input to the testee on the command line
(`convert --type T --value V`). The testee sees nothing else.

## The canon (S2)

Expected values are minted from the reference converter
(`LHLibUtil.objToVarVal`) by the reference testee's `mint` verb, and
frozen. The serde `manifest.json` is also minted. The reference testee's
case list is the single source, so the inputs the runner replays are
exactly the inputs that produced the fixtures.

## The arms denominator (S3)

`surface.json` is generated by reflection over the proto's
`VariableValue.value` oneof, the shared truth every SDK compiles. The
freshness check requires every arm to be covered by at least one fixture
or excused in `exemptions.yaml` with a reason. A new arm landing in the
proto reddens freshness until the exam grows.

## Integers (S4)

`INT` is an int64. It travels as a decimal string in proto3 JSON and in
the manifest, because JSON numbers (and JS numbers) are float64 and
silently lose precision above 2⁵³. The `int-beyond-double` case exists to
make that loss visible instead of silent.

## Embedded JSON, v1 constraints (S5)

The `jsonObj` and `jsonArr` arms hold JSON as a string, so their
comparison is textual and serializer formatting would leak in. v1 corpus
inputs are therefore constrained. At most one key or element, string
leaves only, and no whitespace in the input text. Richer cases require
choosing a cross-SDK canonicalization for embedded JSON. That choice is
deferred deliberately, and it stays cheap to make until such cases exist
(the html5lib lesson, where an under-specified oracle proved expensive to
retrofit).

## Null (S6)

A null input converts to a `VariableValue` with no arm set, which is `{}`
in JSON. This is the `null-value` case. It covers no arm.

## Serialization (S7)

Testees print the `VariableValue` as proto3 JSON (same rules as the
builder's R11). Int64 goes as strings, bytes as base64, and timestamps as
RFC 3339 strings. Comparison is semantic.

## Minting

This area's canon (`surface.json`, `manifest.json`, and every fixture
under `cases/`) is minted by the reference testee's serde module,
[`SerdeAreaMint.java`](../../../sdk-java/conformance/src/main/java/io/littlehorse/sdk/conformance/SerdeAreaMint.java),
which mints from the case list and `convert` answers in `SerdeArea.java`
(S2, one source, so the replayed inputs are provably the inputs that
produced the fixtures). Regenerate only ever inside a PR, where the diff
is the review surface:

```
node sdk-conformance/runner/build.mjs
node sdk-conformance/runner/mint.mjs
```
