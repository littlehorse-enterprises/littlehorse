## What this proposal family is

This directory proposes one shared conformance suite for all LittleHorse
SDKs: a frozen set of test cases with canonical expected answers, which
every SDK runs against, sdk-java included, with the results published as a
matrix anyone can regenerate. "In parity" stops meaning "matched sdk-java"
and starts meaning "passed the same exam."

- [design.md](./design.md) is the v1 architecture, stated in full, with a
  dedicated section on what future versions can entail.
- [adoption.md](./adoption.md) is how SDKs join and how the suite is
  governed.

The design decisions cite a study of how fourteen real multi-language
ecosystems (Protocol Buffers, gRPC, Temporal, AWS, Ethereum, the JSON
Schema and JavaScript test suites, and more) run cross-language
conformance: what survives, and what rots. "The research" and the named
lessons throughout this family refer to that study, whose write-up is not
kept in this repo; the cited systems are all public, so any specific
claim can be re-verified at its source.

## Why a conformance suite

Bilateral parity, meaning verifying one SDK directly against sdk-java, can
be made rigorous: test lists derived from sdk-java's public surface,
expected values generated by running real sdk-java, exemptions kept in
written, ratcheted ledgers. But however rigorous, it has one structural
asymmetry: sdk-java is the unquestioned reference. Java cannot fail, so
Java's accidents become everyone's standard, and nothing detects when the
gold standard itself drifts.

A conformance suite fixes the asymmetry with one move: the expected
answers are frozen as shared canon, and sdk-java becomes an examinee like
every other SDK. If a future Java refactor changes its compiled output,
Java's own column goes red. A deliberate canon change then requires a
reviewed PR to the suite, not a silent shift in what "correct" means.

It also changes the economics of the other SDKs. LittleHorse has five
(sdk-java, sdk-js, sdk-go, sdk-python, sdk-dotnet). Pairwise parity across
five is ten relationships; one exam is five report cards. And the research
is unambiguous that joining must be nearly free: the surviving suites make
each language's hook a trivial program, and the suites that demanded more
died of non-adoption.

## The values this suite must respect

Every design decision in this family traces to one of these values, each
sharpened by the research:

1. Never state a guarantee; wire it. A claimed check that cannot go red is
   worse than no check. Every property of the suite (canon freshness,
   ledger accuracy, matrix currency) must be enforced by something that
   fails.
2. Expected values are never authored by the SDK under test. Canon is
   generated from a reference through review, or adjudicated by the
   server. No SDK grades its own homework, and once the suite exists that
   includes sdk-java.
3. Judgment lives only in written, ratcheted ledgers. "Not yet" and "never
   applicable" are different states, each entry carries a reason, and an
   excuse that stops being true fails the build until deleted.
4. Joining must cost an afternoon. The per-SDK hook is a small program
   with a few-verb contract. Anything more expensive and SDKs will not
   join; that is the single most consistent finding in the research.
5. The suite rides normal CI or it dies. No manually invoked test suite
   survives. Participation means the suite runs in your ordinary pipeline.
6. Adoption is an invitation, not an imposition. Three rungs (not joined,
   report-only, gated), each honest and visible. No SDK team is forced
   onto the exam; the matrix simply shows where everyone stands.
7. Every published cell is an executed test. The matrix is generated from
   machine results, never self-attested. The research shows self-reported
   compliance tables measure what maintainers say, not what code does.
8. Start narrow and data-shaped. v1 covers exactly one layer (workflow
   compilation) for exactly two SDKs. Every durable suite studied began
   this way.

## What this does for the standing goal

The organization's current priority is sdk-js parity with sdk-java, and
this suite strengthens that claim without detouring from it: sdk-js and
sdk-java both pass the same frozen exam, verified by the same runner,
published in a matrix anyone can regenerate, with Java's own column
proving the reference has not drifted underneath the comparison.

## Review question for this family

The one decision this proposal asks for: should this suite become the
organization's definition of SDK parity, one shared exam that every SDK,
including sdk-java, takes? Everything beyond v1 (more SDKs, runtime cases,
governance transfer) is sequenced in
[design.md](./design.md#future-versions) and can be revisited at each
step.
